# Object-Oriented Programming in Java (OOPJ) Architecture

This document demonstrates how Object-Oriented Programming (OOP) principles and architectural design patterns are implemented across the Spring Boot backend.

---

## 1. Core OOP Principles Applied

### A. Encapsulation
- All entity and DTO fields are declared `private` to prevent unauthorized direct state modification.
- Access to object state is controlled via explicit getters and setters, enforced with Lombok annotations (`@Getter`, `@Setter`) and entity lifecycle methods (e.g. `getFullName()`, `recordAudit()`).
- Data integrity constraints (e.g., `@Column(nullable = false)`, `@Email`, `@NotBlank`) protect state at object boundaries.

```java
public class User {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, unique = true)
    private String email;

    @Column(name = "password_hash", nullable = false)
    private String passwordHash;

    public String getFullName() {
        return firstName + " " + lastName;
    }
}
```

---

### B. Abstraction
- Internal database details and communication mechanisms are abstracted behind clean interfaces.
- The `TicketService` abstracts away the complexity of making HTTP REST requests to the Python ML classifier and executing BFS pathfinding on the escalation graph:
  The calling controller simply invokes `ticketService.createTicket(request, currentUser)` without needing to know whether the classifier is local, remote, or running on FastAPI.

```java
public interface UserRepository extends JpaRepository<User, Long> {
    Optional<User> findByEmail(String email);
    boolean existsByEmail(String email);
}
```

---

### C. Inheritance
- Spring Data JPA entities leverage composition and relationship inheritance (`User` is referenced by both `Customer` and `Agent` profiles).
- The `JwtAuthenticationFilter` inherits from `OncePerRequestFilter`, reusing the request filtering lifecycle and overriding `doFilterInternal()`.
- Standard exception hierarchies inherit from `RuntimeException` (e.g., `IllegalArgumentException`, `IllegalStateException`).

---

### D. Polymorphism
- **Method Overloading**: Methods like `searchTickets()` accept various permutations of optional parameters (status, priority, team, category, search keyword).
- **Interface-based Polymorphism**:
  - `UserDetails` interface is implemented by Spring Security's `User` class.
  - `PasswordEncoder` interface is implemented polymorphically by `BCryptPasswordEncoder`.
  - JPA repository query methods (`findByCustomerId`, `searchTickets`) are dynamically generated by Spring Data proxy implementations.

## 2. Design Patterns Implemented

### 1. Repository Pattern
Separates data access logic from business rules. Domain entities (`Ticket`, `User`, `Team`) interact with persistence mechanisms solely through Repository interfaces extending `JpaRepository`.

### 2. Service Layer Pattern
Encapsulates business workflows (`TicketService`, `ClassificationService`, `EscalationService`, `RoutingService`). Ensures transactional atomicity (`@Transactional`) and audit logging.

### 3. Data Transfer Object (DTO) Pattern
Prevents direct exposure of JPA entities over the HTTP API. DTOs (`TicketRequest`, `TicketResponse`, `AuthResponse`) decouple client communication schemas from the relational database structure, preventing accidental data leaks (e.g. `password_hash`).

### 4. Singleton Pattern
Spring components (`@Service`, `@Component`, `@RestController`) are managed by the Spring IoC container as singleton beans, ensuring single instances of `AdjacencyListGraph` and `WebClient`.

### 5. Strategy Pattern
Ticket categorization and team routing apply strategy selection:
```java
String teamCode = switch (categoryCode) {
    case "BILLING", "REFUND" -> "BILLING_TEAM";
    case "TECHNICAL_SUPPORT" -> "TECH_SUPPORT_TEAM";
    case "ACCOUNT_ACCESS" -> "ACCOUNT_SECURITY_TEAM";
    case "SHIPPING" -> "SHIPPING_TEAM";
    case "PRODUCT_ISSUE" -> "PRODUCT_SUPPORT_TEAM";
    default -> "TECH_SUPPORT_TEAM";
};
```

## 3. SOLID Principles Compliance

- **Single Responsibility Principle (SRP)**: Each class has one defined responsibility (`ClassificationService` handles NLP inference; `EscalationService` manages escalation graph workflows).
- **Open/Closed Principle (OCP)**: New escalation nodes and graph edges can be registered dynamically via `addNode` and `addEdge` without altering the BFS traversal logic.
- **Liskov Substitution Principle (LSP)**: Any `UserDetailsService` implementation can substitute for the default Spring Security provider.
- **Interface Segregation Principle (ISP)**: Focused repository interfaces provide only relevant queries per domain boundary.
- **Dependency Inversion Principle (DIP)**: Controllers and services depend on abstractions (`UserRepository`, `PasswordEncoder`) injected via constructor-based dependency injection (`@RequiredArgsConstructor`).
